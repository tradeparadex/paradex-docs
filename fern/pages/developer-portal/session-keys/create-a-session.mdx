---
title: Create a Session
subtitle: Build a session grant, have the owner sign it, open the session and sign in with the session key
---

Opening a session takes one owner signature and one unauthenticated request. The steps below describe the raw API. The [TypeScript and Python SDKs](/api/session-keys/sdk-examples) build, validate and sign the grant for you.

## 1. Generate a session key

Generate a new Stark key pair for every session. The public key goes into the grant as `sessionKey`; keep the private key in your app. A key that has ever belonged to the account, including the key of a revoked or expired session, is refused with `SESSION_KEY_IN_USE`.

## 2. Build the grant

A `SessionGrant` has these fields. Field names are camelCase and the order shown is the signed order.

| Field | Type | Description |
| --- | --- | --- |
| `paradexChain` | string | The Paradex chain id, the `starknet_chain_id` value from `GET /v1/system/config` |
| `environment` | string | `mainnet` or `testnet` |
| `account` | string | The main account the session is anchored to, as `0x` hex |
| `sessionKey` | string | The session public key, as `0x` hex |
| `label` | string | A name the owner sees for the session, at most 64 printable ASCII characters. May be empty. |
| `scopes` | string[] | The [scopes](/api/session-keys/scopes) the session gets beyond reading. May be empty for a read only session. |
| `limits` | `Limits` | Per session trading limits. See [Limits](#limits). |
| `builder` | `Builder` | A builder fee approval. See [Builder](#builder). |
| `subaccounts` | string[] | Subaccounts of `account` the session may also trade, as `0x` hex. See [Subaccounts](#subaccounts). |
| `nonce` | string | A random nonzero value of at most 128 bits, as lowercase `0x` hex without leading zeros |
| `issuedAt` | uint64 | When the grant was created, in Unix seconds |
| `expiresAt` | uint64 | When the session ends, in Unix seconds |

### Lifetime

`issuedAt` must be within the last 24 hours, which leaves time for multisig owners to collect signatures, and no more than 5 minutes ahead of server time. `expiresAt` must be in the future and at most 30 days after the earlier of `issuedAt` and the time the server receives the grant. A grant that lists `trade:block` or `account:settings` lasts at most 7 days. Seven days is a sensible default for a browser session.

### Limits

`Limits` is part of the signed message and every field must be present:

| Field | Type |
| --- | --- |
| `maxOrderNotional` | string |
| `maxOpenNotional` | string |
| `dailyNotional` | string |
| `maxLoss` | string |
| `maxLeverage` | string |
| `markets` | string[] |

Session limits are not enforced at launch, so the server only accepts a grant that states no limit: every amount set to `"none"` and `markets` set to `["*"]`. Any other value returns `LIMIT_INVALID`. The fields exist so that grants keep the same shape if limits are introduced later. Until then a session can trade up to whatever the account itself can.

```json
{
  "maxOrderNotional": "none",
  "maxOpenNotional": "none",
  "dailyNotional": "none",
  "maxLoss": "none",
  "maxLeverage": "none",
  "markets": ["*"]
}
```

### Builder

`Builder` is also part of every grant. Grants that approve a builder are not accepted yet, so always send the empty builder:

```json
{ "account": "0x0", "maxFeeRate": "0", "expiresAt": 0 }
```

### Subaccounts

An EVM owned account can list up to 32 of its EVM subaccounts, and the session key then signs in to each one separately. A listed address must be an onboarded subaccount that the owner's wallet created under `account` and has not archived. Any other address, including a Starknet subaccount, returns `ACCOUNT_NOT_ELIGIBLE` after the owner has signed, so check the list first. Archiving a subaccount does not end sessions that already cover it.

- The owner's main key session creates an EVM subaccount with `POST /v2/account/subaccounts`, which takes no body and returns its `address` and `index`. Access may be limited during rollout.
- `GET /v2/onboarding/subaccounts?eth_address=<wallet>` lists a wallet's EVM subaccounts, lowest index first, without a JWT, so an app can fill in the grant before it signs in. Archived subaccounts are left out.

Grants from Starknet owned accounts cannot list subaccounts, and neither can a grant that [opens a new account](#open-a-new-account-with-the-first-grant). Only a main account can anchor a grant; a vault operator account can hold a session for itself alone, with no subaccounts.

## 3. Sign the grant

The owner signs the grant as typed data. Both encodings use the domain name `Paradex Session` and version `1`, which differ from the `Paradex` domain used for orders and auth, so a grant prompt never looks like an order.

### The grant id

The grant id identifies the session in every later request. `POST /v2/sessions` returns it, and you can compute it yourself:

- for an EVM owned account, the EIP-712 struct hash of the `SessionGrant` message. It does not include the domain, so it does not depend on the chain the wallet signed on;
- for a Starknet owned account, the SNIP-12 message hash.

Either way it is written as `0x` followed by 64 lowercase hex characters.

## 4. Open the session

`POST /v2/sessions` needs no JWT: the owner's signature is the authentication.

```http
POST /v2/sessions
Content-Type: application/json
```

| Field | Type | Description |
| --- | --- | --- |
| `grant` | object | The `SessionGrant` message as signed, with its camelCase field names. Each field must appear once. Send `issuedAt`, `expiresAt` and `builder.expiresAt` as JSON integers, including for `snip12`, where the signed message writes them as decimal strings. |
| `signature` | string | For `eip712`, the `0x` hex signature: `r`, `s` and `v` concatenated. For `snip12`, the string `'["0xr","0xs"]'`, as orders carry it. A bare `["0xr", "0xs"]` array is also accepted. |
| `signature_type` | string | `eip712` for EVM owned accounts, `snip12` for Starknet owned accounts |
| `signature_chain_id` | integer | The EIP-712 domain `chainId` the wallet signed with. Required for `eip712`, ignored for `snip12`. |
| `referral_code` | string | Optional. Read only when the grant [opens a new account](#open-a-new-account-with-the-first-grant). |
| `marketing_code` | string | Optional. Read only when the grant opens a new account. |
| `utm` | object | Optional `source`, `campaign` and `type`. Read only when the grant opens a new account. |

```json
{
  "grant": { "paradexChain": "...", "environment": "mainnet", "...": "..." },
  "signature": "0x<130 hex characters>",
  "signature_type": "eip712",
  "signature_chain_id": 1
}
```

**Response** `200`

| Field | Type | Description |
| --- | --- | --- |
| `grant_id` | string | The grant id |
| `expires_at` | integer | When the session expires, in milliseconds |
| `accounts` | string[] | Every account the session can trade: the anchor account, then each listed subaccount |

```json
{
  "grant_id": "0x5f1c0a4e2b7d9e3f6a8c1b0d2e4f6a8c0b2d4e6f8a0c2e4b6d8f0a2c4e6b8d0f",
  "expires_at": 1767830400000,
  "accounts": ["0x<account>"]
}
```

Check that `grant_id`, `accounts` and `expires_at` match the grant you signed before you rely on the session.

Each grant can be used once. Sending the same grant again, or another grant with the same nonce, returns `NONCE_REUSED`.

### Open a new account with the first grant

An EVM wallet that has no Paradex account yet can open one with its first session grant, with no separate onboarding call. Sign the grant as usual, with `account` set to the address the server derives for the wallet, and send it to `POST /v2/sessions`. `GET /v1/onboarding?account_signer_type=eip191&eth_address=<wallet>` returns that address, without a JWT. Any other address returns `INVALID_SIGNATURE` after the wallet has signed. The server opens the account and the session together.

- The account is deployed on chain when it is first funded. Until then, RFQ requests return `400 NOT_ONBOARDED`.
- `referral_code`, `marketing_code` and `utm` work as they do for `POST /v2/onboarding`. They are not part of what the wallet signs, and are ignored for an account that already exists.
- The grant cannot list subaccounts.
- The wallet must be an externally owned account. Smart contract wallets cannot sign a grant, so they onboard the usual way.
- The request runs the same checks as onboarding, so it can also return the onboarding errors below.

### Errors

| Status | Error | Meaning |
| --- | --- | --- |
| 400 | `INVALID_SIGNATURE` | The signature is not the account owner's (a smart contract wallet's never is), does not match `signature_type`, or names an account that cannot be verified |
| 400 | `GRANT_EXPIRED` | `expiresAt` has passed, or `issuedAt` is outside the accepted window |
| 400 | `INVALID_ENVIRONMENT` | The grant is for another environment |
| 400 | `INVALID_CHAIN` | The grant is for another Paradex chain |
| 400 | `SCOPE_NOT_ALLOWED` | A scope is unknown or reserved |
| 400 | `LIMIT_INVALID` | A limit is missing, malformed or not `none`, `markets` is not `["*"]`, the grant names a builder, or the expiry is longer than allowed |
| 400 | `NONCE_REUSED` | The grant or its nonce was already used |
| 400 | `ACCOUNT_NOT_ELIGIBLE` | The account or a listed subaccount cannot hold sessions |
| 400 | `INVALID_GRANT` | The grant does not match the `SessionGrant` schema |
| 400 | `SESSION_KEY_IN_USE` | The session key is, or was, a key of a listed account |
| 400 | `SESSION_LIMIT_REACHED` | The account holds the most active sessions it may. Revoke one first. |
| 403 | `SESSIONS_DISABLED` | Sessions are not available for this account yet |

When the grant opens a new account it can also return:

| Status | Error | Meaning |
| --- | --- | --- |
| 400 | `INVALID_MARKETING_CODE` | `marketing_code` is not a known code |
| 400 | `INVALID_REQUEST_PARAMETER` | `marketing_code` is not in the form `campaign:code`, or `utm` lacks `source` or `campaign` |
| 400 | `INSUFFICIENT_MIN_CHAIN_BALANCE` | The wallet does not hold the minimum balance onboarding requires |
| 400 | `ETHEREUM_ADDRESS_BLOCKED` | The wallet failed screening. Also returned for an existing account that is blocked. |
| 400 | `PARENT_ADDRESS_ALREADY_ONBOARDED` | The wallet already owns a different account |
| 400 | `ACCOUNT_NOT_ELIGIBLE` | The grant lists subaccounts, or a new account cannot be opened with a grant |
| 429 | `ONBOARDING_RATE_LIMITED` | Too many new accounts from this IP address. Try again later. |

## 5. Sign in with the session key

The session key signs in like a [subkey](/api/general-information/api-authentication#generating-auth-tokens): call `POST /v1/auth/{public_key}` with the session public key in the path, the account address in `PARADEX-STARKNET-ACCOUNT`, and `PARADEX-STARKNET-SIGNATURE` signed by the session private key. Repeat for each account in `accounts` to get one JWT per account.

The public key in the path is required. `POST /v1/auth` without it checks the signature against the account's main key, so it refuses a session key's signature.

- Sign and send both `PARADEX-TIMESTAMP` and `PARADEX-SIGNATURE-EXPIRATION`. The expiration must be at most 15 minutes after the timestamp and no later than the session's expiry.
- A session JWT lasts at most 15 minutes and never outlives its session. Sign in again to refresh it.
- Once the session is revoked or expired, `/auth` returns `SESSION_REVOKED` or `SESSION_EXPIRED`.
- If the owner has set an [IP allowlist](/api/session-keys/manage-sessions#set-a-sessions-ip-allowlist) for the session, sign in and every later request must come from an allowed IP, or they return `403 IP_NOT_ALLOWED`.

Use the JWT and the session key for REST and WebSocket calls exactly as you would a subkey's: send the JWT as the bearer token, and sign orders with the session private key. Every request is held to the grant's [scopes](/api/session-keys/scopes).
