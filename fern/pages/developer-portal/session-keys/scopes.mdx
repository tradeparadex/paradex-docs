title: Scopes
subtitle: What a session may do, route by route

A grant's `scopes` list what the session may do beyond reading. Read access is always included and is never listed.

| Scope | Grants |
| --- | --- |
| *(read, implied)* | Private reads: orders, fills, positions, balances, account data. Also deposits into the session's own account. |
| `trade` | Create, modify and cancel orders, batches and algo orders |
| `account:settings` | Leverage and margin type, market maker protection, max slippage and display settings |
| `trade:rfq` | Create, execute and cancel RFQs, use RFQ drafts and read RFQs, under the conditions below |
| `trade:block` | Accepted in a grant, but grants nothing yet: block trade writes are owner only |

A grant that lists `account:settings` or `trade:block` lasts at most 7 days.

The scopes `withdraw:owner` and `trade:isolated` are reserved: a grant that lists either is refused with `SCOPE_NOT_ALLOWED`, as is any unknown or repeated scope.

<Note>
Creating, offering, executing or canceling block trades is reserved for the owner, so `trade:block` does not let a session trade today. Every session can read block trades.
</Note>

## How scopes are enforced

Every private route declares the scope a session JWT needs. A session JWT is refused with `403 INVALID_TOKEN_SCOPE` when:

- the route requires a scope the grant does not list;
- the route is reserved for the owner;
- the route has not declared a scope. New private routes are closed to sessions until they do;
- the request names `on_behalf_of_account`;
- the JWT authorizes accounts other than the one it was minted for.

A `403` is a refused action. It does not mean the session has ended. JWTs from main keys, subkeys and API tokens are not affected by scopes.

### Deposits (every session)

| Method | Route |
| --- | --- |
| POST | `/v1/deposit-addresses` |
| POST | `/v1/bridges/layerswap/swaps`: deposits only |

A session can pay into the account it signed in to, and nothing else that moves value. It can create a deposit address, or a Layerswap swap into the account with `use_deposit_address` set to `true` and no `source_address`. A swap out of Paradex, or one without `use_deposit_address`, returns `403 INVALID_TOKEN_SCOPE`. Withdrawals and transfers stay with the owner. Each session has its own deposit rate limit, separate from the owner's and other sessions'.

### `trade:rfq`

Any session whose grant lists `trade:rfq` can use these routes:

| Method | Route |
| --- | --- |
| GET | `/v1/rfqs`, `/v1/rfqs/markets`, `/v1/rfqs/platform-state`, `/v1/rfqs/{rfq_id}/bbo` |
| DELETE | `/v1/rfqs/{rfq_id}` |

These routes also require `trade:rfq`, and more besides:

| Method | Route |
| --- | --- |
| POST | `/v1/rfqs`, `/v1/rfqs/{rfq_id}/execute` |
| GET, POST | `/v1/rfqs/drafts` |
| DELETE | `/v1/rfqs/drafts/{draft_id}` |
| POST | `/v1/account/paradigm/enable` |

An RFQ execution settles as a block trade, which session limits could not bound, so a session can use these routes only when:

- its grant names no builder and caps nothing, with every limit `"none"` and `markets` `["*"]`. Every grant the server accepts today meets this;
- RFQ for sessions is available for the account. Access may be limited during rollout.

Otherwise RFQ create, execute and drafts return `403 REQUEST_NOT_ALLOWED`, and `POST /v1/account/paradigm/enable` returns `403 INVALID_TOKEN_SCOPE`. An account that is not deployed on chain yet, such as one [opened by its first grant](/api/session-keys/create-a-session#open-a-new-account-with-the-first-grant) and not funded, gets `400 NOT_ONBOARDED` on every RFQ route.

A session cannot enable RFQ on an account: `POST /v1/account/paradigm/enable` only tells it whether the owner already has. The owner's main key session makes the first call. A revoked session can no longer execute an RFQ, even one it created.
